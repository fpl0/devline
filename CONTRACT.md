# Devline core protocol

The SwiftUI app and Rust CLI share a Rust core. The macOS app sends JSON to the C bridge on a background task. The CLI calls the same core directly.

## Storage and catalog

The library defaults to `~/Library/Application Support/Devline`. An existing `~/Library/Application Support/DevKit` library is used when the Devline directory is absent. Set `DEVLINE_HOME` or `DEVLINE_CATALOG` to override the library or catalog directory. The earlier `DEVKIT_HOME` and `DEVKIT_CATALOG` names are accepted as fallbacks. Requests may also supply `home` and `catalog` explicitly. The app passes its bundled `Resources/catalog` path by default.

The catalog contains `catalog.json`, `docs/`, `templates/`, and `infrastructure.json`. `catalog.json` has `schema_version: 1` and combines the `docs` and `templates` arrays from `docs-catalog.json` and `templates-catalog.json`.

- A documentation pack specifies `id`, `name`, `stack`, `version`, `description`, `source_url`, `license`, and `path`. Its directory contains `documents.json`, with `id`, `title`, `body`, `source_url`, optional self-contained sanitized `html`, `aliases`, and `category` per record. A pack can declare `shards` and continue with `documents-2.json` and subsequent numbered files. Include the upstream license and source notices in the pack directory. Installed record IDs take the form `<pack>@<version>/<record>`. Long references may have `::part-N` continuations. Changes to content require a new version. Use `<upstream>+devline.N` for a pack revision that retains its upstream version.
- A pack can describe `upstream_version`, `snapshot_date`, `coverage`, and `omissions`. Project matching uses the upstream version when present. Coverage and omissions are lists of strings. `local_only` defaults to false. Device-local SDK references use true and are excluded from public packaging, distribution manifests, and portable bundles. The reserved `swiftui` family is always local-only, even if incoming metadata omits the flag.
- A pack can declare `markdown` path selectors. A selector is an exact record path or a pattern with one `*` wildcard. For example, `"markdown": ["guides/*.md"]` marks guide bodies for CommonMark and GFM rendering when opened. The response retains the original body. The renderer omits raw HTML and images and limits generated links to HTTP, HTTPS, and local anchors. An empty selector list marks the pack as plaintext. Older bundled catalogs can use built-in format defaults.
- A starter specifies `id`, `name`, `stack`, `version`, `description`, `app_type`, `path`, `toolchain`, `minimum_version`, `test_command`, `docs`, `verified`, and `target`. Its directory contains `project/` and can include a `build-latest.sh` recipe. Document references can pin versions as `<pack>@<version>`. Optional `services` contains exact `<service>@<version>` references suggested when creating a project. Use relative dependency paths and `__PROJECT_NAME__` for the generated name. Release installation and creation verify the local payload, and project creation requires a verified release for the current target.

## C bridge

`char *devline_request(const char *json)` accepts a NUL-terminated UTF-8 JSON request and returns an owned NUL-terminated JSON response. Release it exactly once with `devline_free(char *response)`.

Every request has a `command`. A success response contains `{"ok":true,"data":...}`. A failure contains `{"ok":false,"error":"…"}`. Optional request fields may be omitted.

### Library and documentation

- `library.retention` returns `{keep_latest}`. Pass a boolean `keep_latest` to change the shared library preference. The default is false.
- `library.purge` removes superseded local docsets, starters, and image archives, keeping the newest local release in each family (per platform for images). It returns release counts as `{docs, starters, images}`.
- `catalog` returns `{docs, templates, home}`. Catalog entries include an `installed` flag for their exact version. The templates array also includes locally rebuilt releases.
- `docs.install` takes `{id, version?}`, uses bundled or cached source files, and returns `{id, version, count}`. For `swiftui`, it imports official declarations and documentation comments from the selected local macOS SDK with external networking denied, or reuses the matching private cache. SDK and compiler identity determine the version. `docs.remove` takes `{id, version}` and returns `{removed}`.
- `docs.local.status` takes optional `{id: "swiftui"}` and reports `{id, name, local_only, available, installed, detail, version?, sdk_version?, sdk_build?, toolchain_version?, count?, active_version?}`. It only detects local tools. It never installs or updates Xcode or the SDK.
- `guide.list` returns Devline help entries; `guide.show` takes `{id}` and returns the selected help article. These authored usage guides are separate from publisher references, search, and documentation-readiness counts.
- `docs.search` takes `{query?, stack?, project_path?, project_stack?, pack_id?, version?, category?, limit?, offset?}`. It returns an array of `{id, pack_id, title, stack, version, source_url, category, snippet, match_kind, symbol?, match_text?}`. The categories are `guide`, `api`, `compatibility`, and `reference`. Omit `category` or use `all` to include them all. `match_kind` is `symbol` or `article`, and `match_text` can identify the matched declaration. An empty query browses in title order. Only browse requests use `offset`. The default `limit` is 30 and the maximum is 100.
- An explicit stack, pack, release, or recognized query prefix takes precedence over automatic project selection. Query prefixes such as `py:Path.read_text`, `go,chi:Router`, and `fastapi@0.162.0:First Steps` intersect explicit filters. For unscoped requests, `project_path` selects compatible project releases and pins. The legacy `project_stack` provides a stack fallback. Otherwise, search uses the active installed release or the newest installed release when there is no preference.
- `docs.show` takes `{id, query?, focus_text?, stack?, project_path?, project_stack?, pack_id?, version?, terminal_format?}`. An exact record ID can open an installed revision directly. The response is `{id, pack_id, title, stack, version, source_url, category, body, html, focus_text?}` and, for split articles, `{part, parts, previous_id?, next_id?}` with one-based part numbers. `html` may be null. `focus_text` is a suggested reader jump target. If `terminal_format` is true and the source is Markdown, `terminal_markdown` includes any fence needed to render a continuation.
- `docs.resolve` takes `{url, id?, pack_id?, version?}` and returns `{id, anchor?, focus_text?}` or null when the link cannot be resolved to an installed destination. For stored HTML, a fragment must match a local anchor, a verified replacement, or a standalone article addressed by that fragment. Provide the originating article as `id` to resolve a relative link or stay within its installed release when following links to the same pack.

### Project references

- `project.context` takes `{path}` and returns `{path, stacks, stack, dependencies, pins, docsets}`. It reads supported manifests and lockfiles without executing project code. `path` is the canonical project folder and `stack` is null when there is no single match.
- Dependencies contain `{id, version, requirement, source}`. Pins contain `{id, version}`. Each docset contains `{id, installed_versions, available_versions, prepare_version, version, state, compatible, requirement, detail}`. `prepare_version` is the exact selected or compatible available release that preparation can use; it never substitutes another version for a pin. Available versions include bundled, cached, and checked channel metadata. `state` is `matched`, `pinned`, `unmatched`, `uninstalled`, or `unversioned`. Unknown versions and compatibility are null. A missing pin retains its requested version and shows its absence from `installed_versions`.
- `project.pin` takes `{path, id, version}` and `project.unpin` takes `{path, id}`. Both return the new project context. Pins are stored locally by canonical project folder. An incompatible explicit pin remains selected and is reported with `compatible: false`.
- `project.readiness` takes `{path}` and returns `{path, ready_offline, status, detail, adapter, fingerprint, verified_at, toolchain, toolchain_path, checks, run_command}`. Readiness checks a receipt against the current source, lockfiles, dependency cache, and toolchain.
- `project.prepare` takes `{path, offline?}` and returns the dependency readiness result. It is the lower-level dependency operation: prepare in a staged copy, test with external networking denied, and publish the managed cache and verification receipt on success. `offline: true` verifies from local resources. The native app and CLI `project prepare` use `toolbox.prepare` for complete project preparation. `project.runner` takes `{path}` and returns `{path, adapter, cache, toolchain_path}` for the CLI to run a development command using the local dependency cache.

### Independent documentation releases

- `docs.distribution.status` reads cached state. `docs.distribution.check` retrieves the configured HTTPS manifest. `docs.distribution.configure` takes `{url}`, with an empty URL to clear the channel. All return `{channel_url, checked_at, error, packs}`.
- A pack status contains `{id, name, stack, active_version, installed_versions, latest, releases, state}`. `state` is `available`, `current`, `installable`, or `unavailable`. A manifest is `{schema_version: 1, releases}`. Each release contains `{pack, release_notes, url, size, sha256}` and identifies an immutable archive. The core verifies size, SHA-256, archive structure, and source attribution before installing.
- `docs.distribution.install` takes `{id, version?}` and returns `{id, version, count, active_version, bytes, sha256}`. Omit the version for the newest known release. `docs.distribution.rollback` takes `{id, version?}` and returns `{id, version, active_version}`. Omit the version to activate the previous installed release. Rollback preserves project pins and installed versions.

### Saved and recent references

- `reading.list` returns `{saved, recent}`, each an array of `{id, title, pack_id, stack, version, source_url, installed, saved_at, visited_at, anchor, focus_text}`. Timestamps are Unix seconds or null. Anchor and focus text are nullable. Each list is newest first, and Recent holds the last 100 distinct references.
- `reading.save` and `reading.visit` take `{id, anchor?, focus_text?}` for an installed record. They keep the saved location and the last visit independent. `reading.remove` takes `{id}` and removes only the saved reference. Each mutation returns the current `{saved, recent}` snapshot. Removing a pack leaves its stored references identifiable with `installed: false`.

### Starters and runtimes

Starter commands accept `id` as a family such as `go/chi-api` or a specific release such as `go/chi-api@1.1.0`.

- `templates.list` returns starter releases with their `installed` flags. `templates.install` takes `{id}` and installs from the local catalog. `templates.build` takes `{id}` and runs the online dependency refresh and offline verification before publishing a new local release. Both return `{id, version, path, verified, installed}`.
- `doctor` takes `{id}` and returns `{ready, ready_offline, status, checks, template, verification}`. Each check contains `{name, ok, detail}`. `ready_offline` requires matching local verification evidence. `prepare` takes `{id}`, installs the starter and its related doc packs, and returns `{template, docs, doctor}`.
- `templates.inspect` takes `{id}` and returns `{template, installed, digest, size_bytes, file_count, contents, dependencies, verified_at, verification, ready_offline}`. Contents entries contain `{name, kind}`, and dependency entries contain `{name, version}`. `templates.remove` takes the exact installed `{id}`.
- `new` takes `{id, destination, dry_run?}` and returns `{path, template, version, test_command, toolchain_path, dry_run}`. The parent directory must exist, and the target directory must be available. A dry run performs readiness checks without creating the project. For a generated project with a bundled test script, `test_command` is `./devline.sh test`.
- `new.ready` accepts `{id, destination, dry_run?, offline?, services?, ports?}`. It installs the exact starter and its documentation, prepares required and selected service archives, tests the project in a restricted local environment, and configures its services. An offline request requires existing archives. A dry run previews the selected services and port plan without creating a project or preparing images.
- `runtime.list` returns `{id, name, toolchain, minimum_version, available, path, version, detail, docs, templates}` for each stack represented in the starter catalog. `minimum_version` describes the starter baseline. `detail` reports the detected executable or the specific setup requirement.

Generated projects keep the lifecycle entry point at `devline.sh` and store their launch configuration and provenance at `.devline/config.json` and `.devline/origin.json`. Projects from catalog starters place lifecycle scripts and relocatable bundled dependencies in `.devline/scripts/` and `.devline/packages/`. Imported starters outside the catalog retain their own script and dependency paths. Prepared dependency caches and local service configuration use `.devline/cache/` and `.devline/services/` as needed. Projects created with earlier releases retain support for their existing paths.

### Offline readiness and bundles

- `offline.status` takes `{path?, docs?, starters?}` and returns `{ready_offline, status, docs, starters, runtimes, project}`. The optional path adds project-selected docs, toolchain checks, and the starter recorded in a generated project. The status is `ready_offline`, `needs_preparation`, or `no_selection`.
- `offline.check` takes `{id}`, runs the installed starter in a fresh environment with external networking denied, and returns `{ready_offline, status, template, verification}`. The verification records the release digest, toolchain, target, and timestamp.
- `bundle.export` takes `{path, docs?, starters?}` and returns `{path, size_bytes, docs, starters}` with counts. Export requires at least one exact `id@version`. `bundle.inspect` takes `{path}` and returns `{compatible, problems, warnings, requirements, requires_trust, trust_starters, docs, starters, size_bytes, unpacked_bytes, file_count}`.
- `bundle.import` takes `{path, trust_starters?}` and returns `{docs, starters, imported}`. It validates the bundle’s manifest and digests before installing. Starter releases outside the bundled catalog require explicit trust. The compressed bundle contains release files and metadata. Toolchains and local readiness evidence remain on the machine where they were detected.

### Local infrastructure and toolbox

The infrastructure catalog has `{schema_version: 1, services}`. A service has an exact `id@version` reference and a platform. The `image` object includes `registry`, `repository`, `tag`, `index_digest`, `digest` for the platform manifest, `config_digest` for the image ID, `platform`, and `compressed_bytes`. Service settings include `ports`, `env`, `volumes`, `command`, `healthcheck`, `provenance`, and an optional exact `docs_ref`. Local interpolation resolves `{{secret:NAME}}` and `{{port:ID}}` for the configured project.

- `infra.catalog` returns `{services, platform}` and retains locally archived catalog releases alongside current bundled entries. `infra.status` takes optional `{id}` and returns `{docker, images}`. A Docker status has `available`, with `endpoint`, `platform`, and `detail` when applicable.
- Image status reports `{id, version, platform, archived, loaded, ready_offline, integrity, status, receipt}`. `archived` reports the archive file's presence and size. `integrity` distinguishes a verified archive, changed metadata, and a missing archive. A receipt records `{id, version, platform, source, source_digest, image_id, archive_sha256, size_bytes, verified_at}`.
- `infra.prepare`, `infra.verify`, and `infra.restore` take `{id}` and return image status. Prepare retrieves the exact pinned platform image if needed and saves an independent verified archive. Verify checks the archive locally. Restore loads the matching archive into a compatible local Docker engine without pulling. `infra.remove` removes the archive and returns `{id, version, removed}`.
- `infra.export` takes `{path, images}` with exact references and returns `{path, images, size_bytes}`. `infra.import.inspect` takes `{path}` and returns `{images, requires_trust, manifest_sha256}`. `infra.import` takes `{path, trust_images?, manifest_sha256?}` and verifies image identities, hashes, platform, and archive structure before returning `{images, imported}`. Unknown image pins require explicit trust. The optional manifest hash binds import to a previous inspection. Move project data, credentials, and toolchains separately.
- `infra.updates` reads cached publisher observations, and `infra.updates.check` refreshes them online. Both take optional `{id}` and return `{checked_at, items}`. Each item contains `{id, name, current_version, available_version, state, detail, reference, checked_at}`. `infra.update` takes `{id}` and prepares a checked release.
- `infra.stack.create` takes `{path, services, ports?}`. Services are exact references. The optional port map uses `service:port-id` keys and local host port values. The generated Compose project binds ports to IPv4 loopback, uses locally generated credentials, and gives services named data volumes.
- `infra.stack.config`, `infra.stack.status`, `infra.stack.up`, `infra.stack.down`, and `infra.stack.logs` take `{path}`. Stack responses include `{path, project_name, configured, services}`, with Docker status, containers, readiness, or log output when requested. Start uses `--no-build --pull never`. Stop preserves named volumes unless the request explicitly sets `delete_volumes: true`. Logs accept an optional `tail`. `infra.stack.credentials` explicitly returns `{path, credentials, connections}`.
- `toolbox.status` and `toolbox.check` take `{path?, docs?, starters?, images?}` and return `{path, ready_offline, status, library, infrastructure, docker, images, project_dependencies, blockers}`. Check verifies selected image archives from disk. An open project reports `project_dependencies.state: verified_project` when its current source and dependency cache match a verified receipt. Its original starter is provenance, not a library prerequisite; an explicit `starters` selection still requires that release.
- `toolbox.prepare` takes `{path, offline?, docs?, starters?, images?}`. It prepares selected compatible or pinned documentation, exact configured image archives, and project dependencies, then returns the complete toolbox status plus `{steps, prepared}`. Each step includes `{kind, id, status, detail?}` and may include a component result. Component failures remain in `blockers`; successful work is retained. A per-project lock serializes preparation. Existing dependencies are tested locally before attempting online preparation. Offline mode does not fetch. Preparation does not manage runtimes, start containers, or change project pins.

### Jobs

- `jobs.start` takes `{kind, id?, version?, path?, docs?, starters?, images?, offline?, trust_starters?, trust_images?, manifest_sha256?, timeout_seconds?}`. Supported kinds are `build`, `verify`, `prepare`, `project_prepare`, `toolbox_prepare`, `content_check`, `content_update`, `docs_prepare` for local docs, `docs_install` for remote docs, `bundle_export`, `bundle_import`, `infra_prepare`, `infra_verify`, `infra_restore`, `infra_export`, `infra_import`, `infra_update`, `infra_stack_up`, and `infra_stack_down`.
- `jobs.list` returns job records. `jobs.status` takes `{job_id, offset?}` and adds `{log, offset, next_offset}` using byte offsets. `jobs.cancel` takes `{job_id}` and returns the record with `cancel_requested`. Records include `{id, kind, target_path, target_reference, state, stage, created_at, started_at, updated_at, result, error}` and may include progress bytes. Targets are nullable for older records. List, status, and cancel include `log_path`. States are `queued`, `running`, `succeeded`, `failed`, and `cancelled`. Incomplete preparation or content updates fail with their structured partial result retained.

### Editor lookup

`devline://search?q=…&path=…&stack=…` opens a symbol search in the desktop app. Percent-encode each value. `path` is an optional absolute local file or directory and `stack` is a fallback language hint. `devline://docs?id=…&anchor=…&focus=…` opens a versioned record and may carry an anchor or focus text. The `devkit` URL scheme is accepted for compatibility.

### Updates

`updates.status` combines cached documentation distribution, starter dependency, image publisher, runtime, app, and local SDK observations. `updates.check` refreshes online sources and records their results; `offline: true` rejects an online check. `updates.configure` takes `{url}` and sets the HTTPS app manifest URL. An empty string disables app checks. Configure does not fetch the manifest.

`updates.runtime.status` reads only cached publisher observations for detected toolchains and returns `{checked_at, items}` without fetching.

`updates.app.status` reads only the saved app release. `updates.app.check` explicitly refreshes only the configured app manifest and rejects `offline: true`. Both return `{checked_at, items}` with one app item. App-only freshness is independent of the content-source check timestamps.

Status and check return `{checked_at, all_checked, items, sources, available_content}`, with `checked_at` in Unix seconds or null. A source reports `{id, name, state, checked_at, detail}`. Each item contains `{id, kind, name, current_version, available_version, state, detail, action, reference, url}`. `kind` is `docs`, `template`, `image`, `runtime`, or `app`. `state` is `current`, `available`, `unchecked`, `error`, or `unconfigured`. Content actions are `install_docs`, `prepare_local_docs`, `install_template`, `rebuild_template`, and `update_image`, each using `reference`. `open_url` uses `url`. Runtime and app actions remain separate from content preparation.

`updates.apply` takes optional `{offline, id}` and applies checked available content updates for installed documentation/starter families and archived image families. It returns `{status, complete, ready, updated, failed, steps, snapshot}`. Each step includes `{id, name, action, reference?, state, detail}`. It preserves project pins, follows the library’s retention setting, retains successful work after another item fails, and serializes bulk updates. Offline mode permits local/cached documentation and bundled starters but reports network-dependent work as blocked. `content_check` and `content_update` expose these operations as cancellable jobs. The CLI uses `updates check [--background]` and `updates apply [ITEM] [--background]`. The optional selector is an update item ID or exact release reference. Unfinished exact targets are persisted before execution and returned with `pending: true`; retries repeat preparation and verification, and clear the target only after success.

With `confirmed_only: true`, bulk apply reports the outcomes of available updates; missing or failed publisher checks remain in `snapshot.sources` and do not count as installation failures. The macOS Updates screen uses this mode.

The release-link manifest is `{"schema_version":1,"version":"0.6.0","url":"https://example.com/releases/0.6.0"}`. Use HTTPS URLs without credentials, queries, or fragments. Its default channel is `release.json` on the latest Devline GitHub release. The macOS app separately uses Sparkle with the bundled public Ed25519 key and requires signed appcasts and archives before installation. Version 0.6.0 uses direct GitHub downloads and has no signed appcast. [Devline releases](https://github.com/fpl0/devline/releases/latest)
